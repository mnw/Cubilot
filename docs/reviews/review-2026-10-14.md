## P1: fix before pushing

### R1. Harness detection regression for pre-existing pi sessions [verified]
**Where:** `src-tauri/src/pty.rs:248-326` (`command_executable`, `harness_from_command`, `pane_harness` fallback)

tmux returns `#{pane_start_command}` wrapped in double quotes, e.g. `"CHATBRIDGE_AGENT='a' '/bin/sleep' 30"` (checked on bundled tmux 3.5a). `command_executable` reads the whole quoted string as one word that starts with `CHATBRIDGE_AGENT=`. It skips that word as an env assignment, finds no next word, and returns `None`, so the harness defaults to `claude`.

**Failure:** any pi session started by a build before `@a2a_harness` existed (tmux sessions survive restarts) is now detected as claude. `slash_discover_for_agent` (`lib.rs:1131`) and `ui/features/slash-command.js:233` then offer claude slash commands to a pi agent. The old `contains("CHATBRIDGE_AGENT=")` check was correct for these legacy panes.

**Why tests miss it:** the unit tests pass unquoted strings, which tmux never returns.

**Fix:** strip one level of tmux quoting (`"` … `"`, unescaping `\"`, `\\` and `\$`) before parsing. Alternatively, keep the old heuristic while `@a2a_harness` is unset, or write `@a2a_harness` onto the session at re-attach. Add a test fed with real tmux output.

### B1. Agent is woken right after the human aborts the turn [verified]
**Where:** `hub/channel/claude-mod/register.ts:247-253`

`turn.complete` calls `bridge?.onRunEnd()` whatever `e.reason` is (`'answer' | 'aborted' | 'refusal' | 'error'`).

**Failure:** the agent reads a DM, then the human presses Esc. `onRunEnd` finds an armed check and submits `NUDGE_TEXT` in wake mode, which starts a new turn immediately after the human stopped the agent. After a context-limit error it starts a turn that will probably fail again.

**Fix:** call `onRunEnd()` only when `e.reason === "answer"`. For the other reasons, clear the armed checks without nudging (for example, a new core method `onRunAborted()`). Also check whether pi's `agent_end` fires on abort.

### B2. Subagent `turn.start` leaves `BUSY` stuck at true [verified]
**Where:** `register.ts:241-245`

The comment says "turn.start is main-loop only: a subagent's run raises none", but the 2.1.296 declarations say `turn.start` fires for subagents too, with `e.agentId` set. The `turn.complete` handler filters on `agentId`; `turn.start` does not.

**Failure:** a background subagent starts after the main loop goes idle, so `BUSY` becomes true and nothing ever clears it. An `interrupt.new` (steer) is then appended without waking the idle agent, and stays undelivered until some later main turn completes.

**Fix:** set `BUSY` only when `!e.agentId`, and fix the comment. Add a test.

### T1. Approval route overwrites an approval the human already granted [verified]
**Where:** `hub/kinds/ticket.ts:457-466`, called from the two-step tool flow at `hub/channel/tools.ts:410-415`

The route reuses the existing pointer only when that request is `pending`. In every other case, including `allowed` by the human, it creates a new request and moves the pointer.

**Failure:**
1. `transition_ticket(done)` gets a 409 because R1 is still pending.
2. The human clicks Allow on R1 while the tool is between calls.
3. The tool calls `POST /tickets/:id/approval`, which sees R1 is `allowed` (not `pending`), creates R2 and moves the pointer.
4. The human's approval is discarded and a second card appears.

**Fix:** if the pointer names a request with `status='allowed' AND resolved_by=<human>`, return it with `created:false`, and have the tool retry the transition once. `openspec/changes/ticket-kind/specs/work-tickets/spec.md` ("Otherwise it SHALL create…") currently requires the buggy behaviour, so update the spec in the same change.

### T2. Assignee is never woken after the human approves `ticket:done` [verified]
**Where:** `hub/channel/core.ts:57-62`, tool text at `hub/channel/tools.ts:421`

`permission.resolved` is in `CONTEXT_KINDS`, and every `ticket.*` event is delivered in `context` mode. Neither starts a turn.

**Failure:** the tool tells the agent to "wait for the human to Allow, then call transition_ticket again", so the agent ends its turn. The human clicks Allow and nothing wakes the agent. The ticket stays `in_review` until someone nudges the agent in chat.

**Fix:** in `modeFor`, return `wake` for a `permission.resolved` with `tool_name === "ticket:done"` whose requesting agent is this agent.

### B3. Room permission card silently dropped for large or non-ASCII tool inputs
**Where:** `register.ts:172`; hub cap `PERMISSION_BODY_MAX = 16_384` at `hub/kinds/permission.ts:56`, enforced on `Content-Length` (`hub/core/auth.ts:91`)

`input_preview` is `JSON.stringify(toolInput).slice(0, 8000)`. That counts UTF-16 code units, and the result is JSON-encoded again inside the body. A Write of CJK text measured 24,053 bytes.

**Failure:** the hub returns 413 and the relay returns null with no log line. Only the local dialog appears, and the room never sees the request.

**Fix:** truncate by the UTF-8 byte length of the encoded body (about 12 KB, measured with `TextEncoder`), or raise the hub cap. Add a test with a large non-ASCII input.

## P2: fix soon

### Bridge (`hub/channel/**`)

**B4. A refused `prompt.submit` loses the message.** `register.ts:69-84, 120-125`; `core.ts:139-153`
- When submit resolves `{ drop }` (Stop hook, host limit, queue full), the only trace is a debug-level `ui.log`.
- `deliver` doesn't await the submit, so it always resolves. This breaks the `host.ts` contract ("Resolves once the runtime has ACCEPTED") and means the core's `catch → checks.delete` path can never run.
- **Effect:** the DM is lost while the hub counts it as delivered. Each refused delivery also leaves an `{armed:false}` entry in `checks` for good.
- **Fix:** on refusal, fall back to `append` (context) or log a warning. Remove the check either way.

**B5. User `PreToolUse` / `PostToolUse` settings hooks never run for chatbridge tools.** `register.ts:264-276`
- The mod answers `tool.call` itself and never calls `next(e)`. Per the declarations, `$.tool.check` "runs no classic hook".
- **Effect:** a user `PreToolUse` hook guarding `mcp__chatbridge__post` is silently skipped. This is the same class of bypass the `$.tool.check` rule exists to prevent.
- Derived from the declarations; not tested live.
- **Fix:** add it to CLAUDE.md as a known limitation, or route chatbridge calls through core.

**B6. curl reads the user's `~/.curlrc`.** `register.ts:62, 115`
- `curl -K -` still loads `~/.curlrc`; only `-q` as the first argument prevents that.
- **Effect:** a user `proxy` setting would send the bearer token through the proxy, and `output` or `fail` settings change every hub request.
- **Fix:** use `["curl", "-q", "-K", "-"]` and add `noproxy = "*"`.

**B7. Stream failures aren't logged, and the relay skips the 401 re-read.** `register.ts:113-119, 186-210`; `node-host.ts:59`
- A curl `--fail` exit (401) or a refused connection ends the stream normally. The exit code is ignored and the core retries every 2 s with no log line, so a stale token loops silently.
- `relayPermission` calls `h.request` directly instead of going through `hub-client`, so it has no 401 token re-read. The final `wait(0)` also reuses the hub URL resolved at the start.
- **Fix:** log the exit code or non-ok status once per failure streak, and route the relay through `hub-client`.

**B8. An old stream can take the next event after `stop()`.** `register.ts:113-119`
- The mod's `stream` checks `signal.aborted` only when a chunk arrives, so the old curl lives until the next heartbeat (up to about 15 s).
- The hub has one queue per agent and the older waiter is first in line, so after a `session.start` restart the first event can go to the dead connection and be dropped.
- **Fix:** abort the spawned process as soon as the signal fires.

**B9. A finished-request id collision isn't retried.** `register.ts:181-182`
- `POST /permissions` returns 409 when the id belongs to an already-resolved request (`permission.ts:145-146`). The mod returns null instead of retrying with a fresh id.
- Permissions never expire and ticket approvals share the id space, so the chance of a collision grows over time.
- **Fix:** retry with a fresh id on 409.

### Tickets (`hub/kinds/ticket.ts`)

**T3. Approval requests that no longer apply stay pending forever.** Rework branch `ticket.ts:263`; cancel and the human's direct `done` (`:244-273`); replay `permission.ts:416-420`
- Rework clears the pointer, and cancel or a direct `done` make the request moot, but none of them resolves the outstanding `ticket:done` request. Permissions have no TTL.
- **Effect:** duplicate "Approve completion of ticket …" cards. Allowing the stale one does nothing, and it is replayed to the assignee on every reconnect.
- **Fix:** dismiss the old request after the commit, as a separate transaction (the one-event-per-transaction rule forbids combining the two). Or hide `ticket:done` cards that aren't the live pointer.

**T4. Other agents are woken to vote on a request only the human's vote can satisfy.** `core.ts:63-66`; `ack_permission` description at `tools.ts:301-304`
- `permission.new` from the assignee wakes every other agent in the room.
- **Effect:** if another agent acks it, the request becomes final with that agent as `resolved_by`. The human's Allow then gets a 409, the gate stays closed, and the assignee isn't woken (see T2).
- **Fix:** deliver `ticket:done` `permission.new` in `context` mode (or drop it) for agents other than the assignee.

**T5. Agents can read tickets from other rooms.** `tools.ts:433,437`; `GET /tickets` at `ticket.ts:490-524`
- `list_tickets({room:"B"})` from an agent in room A returns B's titles and acceptance criteria.
- **Fix:** drop the `room` argument from the tool and always use `ctx.room`. The webview still needs the hub route as it is.

### Pause (`hub/features/chat.ts`, `ui/terminal.js`)

**P1. Hub drops the pause but the UI keeps showing it.** `hub/core/agents.ts:100-110`; `hub/features/chat.ts:24-28`; `ui/terminal.js:378-387`; `ui/main.js:98-101`
- `remove()` (stale timer, `/remove`, the × on a legend pill) drops the Agent object, so the WeakSet pause goes with it. Nothing announces this.
- The UI only re-reads pause state on SSE `onopen`, on pause entries, and in `ensureTab`. `applyRoster` and `applyPresence` never do.
- **Effect:** the tab still shows "paused" while broadcasts reach the agent. The next click sends `{paused:false}`, which does nothing, so the user must click twice.
- `PAUSED_AGENTS` is also never cleaned up in `removeTab`.
- **Fix:** call `syncAllPauseStates()` from `applyRoster`, and delete the agent from `PAUSED_AGENTS` in `removeTab`.

**P2. Pause survives kill + respawn within 15 s.** `hub/core/agents.ts:83-89`
- `ensure()` returns the same Agent object while the stale timer is pending, so a quick respawn (for example, to change the agent's room) starts paused.
- This contradicts the 5d55af7 commit message. The test only covers an explicit `/remove`.
- **Fix:** decide which behaviour is intended. If a fresh spawn should start unpaused, clear the pause on the spawn path.

### Rust shell (`src-tauri/`)

**R2. Version parsing rejects valid versions.** `pty.rs:489` `parse_claude_version`
- Each part must parse as `u32`, so `2.1.300-beta.1` or `2.1.300+abc` fails, as does any output with a line before the version.
- **Effect:** the user is refused with "version could not be read".
- **Fix:** take the leading digits of each part, and search all output lines for the first `\d+\.\d+\.\d+`.

**R3. Misleading error for a missing or broken `claude_path`.** `pty.rs:479, 496-537`
- Spawn failure, non-zero exit, timeout and unparseable output all collapse into one error that suggests `npm update -g`. Native installs update with `claude update` instead.
- **Fix:** give each case its own error, include the path and raw output, and make the update hint independent of the install method.

**R4. Version check can freeze the UI for up to 10 s.** `pty.rs:509-534`
- `pty_spawn` is a sync `#[tauri::command]`, which runs on the main thread, and every new claude spawn now runs `claude --version`.
- **Fix:** use `#[tauri::command(async)]` or a worker thread, and consider a 2–3 s timeout.

**R5. Staging race between two app instances.** `lib.rs:764-805` `stage_chatbridge_mod`
- The swap is two renames with a gap between them. If another instance renames its temp dir into `dest` during that gap, this instance's rename fails with ENOTEMPTY and its rollback fails too.
- **Effect:** `.chatbridge-mod.old-<pid>` is left behind. Any claude started during the gap loads no mod.
- **Fix:** `renamex_np(tmp, dest, RENAME_SWAP)` (atomic on APFS), or an advisory `flock` around staging.

## Trust model note

Any agent with Bash can read `hub.token` and send `by:"human"`. That lets it:
- open the ticket approval gate (directly, or through `/permissions/<id>/verdict`);
- pause or unpause any agent;
- dismiss any permission request in any room.

CLAUDE.md already accepts trust-on-self-assertion, but the efa88f4 commit message ("an agent's Allow never opens the gate") only holds for agents that report their own name honestly. Until per-agent tokens exist, document `blast_radius: high` as advisory, not enforced.

### Source-confirmed findings and narrower conclusions

- **B4: valid refusal cleanup/observability issue.** The adapter logs refusals, does not call `onRead`, and does not propagate them to the core. Unarmed checks then have no removal path. Existing native tests already cover refused submit logging and no phantom read. Cleanup is the missing regression. Do not automatically append a prompt rejected by a Stop hook or another policy guard. That could bypass the refusal. Make rejection observable and release its check.
- **B5: PARTLY, with live behavior still unverified.** `$.tool.check` explicitly runs no `PreToolUse` hook. The mod answers its own call without `next(e)`. User-hook parity is therefore a legitimate concern. These declarations do not independently prove that every `PostToolUse` hook is skipped by the outer engine. They also state that managed-settings deny comes first. Do not describe this as a bypass of all permission policy. Document the confirmed scope, and test real user settings before promising a core-routing fix.
- **B6: valid isolation concern from source and curl's documented defaults.** Both command vectors lack first-argument `-q`, and neither config suppresses proxies. Reviewer did not rerun the denied curl probe. A fix should cover both request/upload and streaming paths. Do not assume a proxy always applies on machines that already configure `NO_PROXY` for loopback.
- **B7: PARTLY.** Silent non-ok stream endings and the relay's frozen token/URL are real. A permanent stale-token stream loop is not established: the core resolves discovery again on every reconnect. Keep those two paths distinct. The relay should preserve bounded requests, exact request ownership, and local fallback when the old hub no longer has the request.
- **B10: valid pre-existing gap.** `briefingSignature()` includes summary counts, while `BridgeEvent` and `renderBriefing()` omit `room_summary`. Summary content is absent, not merely redundantly re-sent. Treat it as pre-existing work, not a ticket-kind regression.

The mod only adopts fresh 201, so it does not consume a colliding pending request's verdict. A separate ticket id namespace can still reduce contention. The alphabet has **25** letters, so the space is `25^5 = 9,765,625`. The DEV3 section's `24^5` figure needs correction.
- **T8: deliberate contract choice, not an implementation defect.** Approval pointer installation writes one permission event with its atomic ticket side effect.
