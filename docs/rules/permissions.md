# Rules: permissions

Permission relay, no-TTL rule and trust-model accepted risks.

## An agent's by and from are self-asserted

- **Mutating structured-message endpoints use trust-on-self-assertion for agents.** `by` and `from` are validated against the expected actor for the route but not cryptographically verified. An agent token holder can claim any agent identity. Documented hardening target: per-sidecar tokens bound to agent identity. The human is not self-asserted: see the item on the human token below.

## Permission relay is a hub-first wait in the `classic.PermissionRequest` hook

- **Permission relay is a hub-first wait in the `classic.PermissionRequest` hook.** The hook `POST /permissions`, then waits on `GET /permissions/:id/wait?timeout_ms=<n>` (default 60 000, hub cap 300 000). `allowed`/`denied` answers the hook, and the local dialog closes without a local answer. On timeout it `POST /permissions/:id/dismiss`es as the agent: 2xx → `next(e)`, so the decision stays with Claude's local dialog; 409 → a verdict won the race, re-read the snapshot (`wait?timeout_ms=0`) and honour it; any other dismiss failure → re-read once, honour a terminal verdict, else `next(e)`. **Every request in the hook is bounded** (`curl --max-time`; the wait passes `timeout_ms + 5000`) — the hook must never hang. Hub unreachable or POST rejected → `next(e)`. On Claude Code 2.1.296 (verified live, M18) the local dialog opens immediately, concurrently with the hook: the room and the terminal race and the first answer wins. A room verdict applies through the hook and closes the dialog; a terminal answer decides at once. After a terminal No the card is dismissed within ~50 ms and a later room click gets 409 (observed on install 9; mechanism not traced). After a terminal Yes the hook keeps waiting until its timeout, then dismisses the room card (it stays visible for up to 60 s; a room click in that window is recorded at the hub but has no effect — known limitation, there is no native signal for a local Yes, and the earlier tool.call-entry heuristic was wrong because the permission prompt runs beneath tool.call's next(e)). On 2.1.287 the dialog waited for the hook (observed in M15/M16). A verdict needs the human token (`POST /permissions/<id>/verdict` is human-only); `hub.token` gates the other `/permissions/*` routes; if a future deploy mode drops auth there, the relay hook must be removed in the same change.

## Permissions have no TTL

- **Permissions have no TTL.** Claude Code's local dialog owns the effective timeout. Never add auto-expiry to the `permissions` table — auto-denying a tool the human actually wanted is annoying, auto-allowing is a security violation, and there is no safe default. Policy-driven per-tool timeouts may land later as a separate feature.

## An agent with an unrestricted shell is the human's OS user, so `blast_radius: high` is advisory

- **An agent with an unrestricted shell is the human's OS user, so `blast_radius: high` is advisory.** The hub has two tokens (hub-first-browser, group 11). `hub.token` is the agent token. The human token goes from the shell to the hub on stdin and to the window through `get_hub_url`: no file and no env value holds it. Each request has a caller, and the human is known by the credential. An agent caller that names the human in `by`, `from`, `actor`, `voter`, `requester`, `agent` or `creator` gets 403 (`the human acts only from the UI`). The routes that only the human may call (`RouteDef.caller: "human"`: request Approve, decision answer, checkpoint create, room settings, agent pause, `/remove`, permission verdict, agent skill writes `PUT /agents/<name>/skills` and `POST /agents/<name>/skills/apply`) give 403 to the agent token, also without a `by`. `/stream` refuses the agent token and `/agent-stream` refuses the human token. This stops a forged `by` over HTTP. It does not stop a hostile local process: an agent with an unrestricted shell runs as the same OS user, so it can read the memory and the process list of the app and the window. Accepted. P6-03 does not change this: the radius rule sets a floor for honest callers. Do not describe a radius, an Approve or a decision as enforcement against a hostile local process.
- **`POST /permissions/<id>/verdict` is human-only; `POST /permissions/<id>/dismiss` stays open to an agent caller.** Peer verdicts end: an agent caller gets 403 on the verdict route. This is the one difference from design decision 5. The mod hook dismisses its own request with the agent token (`hub/channel/claude-mod/register.ts`). Without that, a timed-out request stays pending, because permissions have no TTL. Risk: the agent token is shared, so an agent can claim the requesting agent's name and dismiss a pending request of another agent. That request falls back to the local prompt. The actor guard still refuses an agent that names the human there.

## Who decides what

- **The human approves.** One Approve per request releases its draft tickets, and later tickets of it (L1). Only the human approves a request, answers a decision (`escalate`) and changes the origin of a request. A high ticket has no Allow step: it closes on the full suite and two Validator PASSes (P6-04). No route and no `ticket:done` permission exist for it.
- **The radius has a floor.** The radius rule (terms and paths in `config.yml`, `hub/core/radius-rule.ts`) gives the lowest `blast_radius` of a ticket text. Exception: a title that starts with `[doc]` ignores the terms; a rule path still counts. The stored radius is never below it. The room lead, the creator or the human raises a radius with `edit_ticket`. Only the human lowers it below the rule. A permission request (`/permissions`) is for a Claude Code tool call and has no link to the radius.
- **The room lead opens, the human answers.** Only the room lead opens a decision. Another agent and the human get 403. Only the human answers it.
