02Roles, models and skills

Each role file and its skills exist in factory/<role>/. Launching an agent with its role is planned work (§2). Core skills listed; optional skills are in the factory README.

Orchestrator

Claude · opus
Both tracks · room lead

Turns requests into user stories (Given/When/Then, INVEST) with agent notes for the facts, keeps every slot busy, answers the Validator's spec findings, checks each PASS, merges into staging and closes the ticket. Parks a ticket after two FAILs and asks you; the rest goes on.

skills
user-stories (factory, new), planning-and-task-breakdown, git-workflow-and-versioning, context-engineering, intent-driven-development, team-agent-orchestration, project-manager-senior
optional
interview-me, constraint-driven-development, architecture-decision-records
never
writes code or docs, tests, reviews

Worker ×N

Claude · sonnet
Technical track · developer

Tests first, implements on its own branch and worktree, kills surviving mutants, answers findings with fixes or evidence.

skills
test-driven-development, incremental-implementation, debugging-and-error-recovery, git-workflow-and-versioning, search-first, coding-standards, minimal-change-engineer
optional
api-design (merged), deprecation-and-migration, frontend-ui-engineering, code-simplification, cms-developer (Drupal)
never
merges, releases, judges own work

The Orchestrator gets one line per failure: cause, evidence, action taken. The ticket shows Why it failed with a link to the trace. A repeat with the same cause key goes onto the open ticket. Only you can cancel with ignore; that key stays quiet until you reopen the ticket. A gap ticket is Done only when its synthetic test and the full suite pass. A diagnosis that runs past 15 min escalates. Secrets are masked before writing; records are deleted after 30 days. Patterns: once a day, after 10 records, or when one category occurs 3 times in an hour, one opus run reads the new records, the metrics of every stage (also PASS: duration, turns, tokens, repeated tool calls) and your right/wrong marks from Needs you, and proposes gap tickets.

04Mutation testing pipeline

Runs inside the technical track, on the files the ticket changed only (§13). The triage step sends code to TypeSafe through OpenRouter, so a project setting keeps it off by default.

Doctor: project checkstack from composer.json, package.json…; tool and PCOV/Xdebug present
→
Tester: mutation runInfection, StrykerJS, mutmut, PIT, cargo-mutants; JSON report
→
Tester: jtt triageJev answers 12 questions per survivoronly if mutation_triage = on
→
Bandsact · review · ignore
→
Validatoradvisory: suggestions only · enforce: open act blocks unless marked equivalent
→
Workerwrites killing tests from agent-prompt.md

Mode per project: mutation_mode: off | advisory | enforce, default off. Advisory first, to learn the real scores. Fast suites only (unit + kernel), 15-min time budget, a partial result never blocks. No jtt for PHP/Drupal → in enforce the Validator applies the project's mutation_threshold, set from the advisory results.

Data: scores and act/review/ignore counts go into the review kind, and the dashboard Quality panel shows them per code ticket (§11).

06Build order

Part 18, the lean flow, came first (decision 2026-10-29): it moved the checking from the plan to the code and removed the human gates between the Approve and the delivery. Before that, the migration came first, then the rebrand, so Cubilot runs beside the previous app without touching it. Parts 1 to 4 give a working factory with fresh sessions, and 4a gives the agent column that Part 4 needs for its tests. Part 6 comes next, before Part 5 (decision 2026-10-26): review format and model routing make the agents more reliable, and delivery and backup is a local item that can wait. Part 12 follows Part 6 (decision 2026-10-27): the desktop app approach is limiting, so the hub serves the UI to any browser and can run on Linux before the later parts are built. The token system and the mockups are done (28 Oct, design/); Part 14 builds them after Part 12, so the redesign is done once, on the browser UI. The design team step is folded into the design council (decision 2026-10-28). Parts 7 and 8 add toolchain and setup; 11 and 13 improve it. The councils (9, 16, 10, 17) come last: the right direction, but much code and testing (decision 2026-10-28). The arbiter (19) waits for the Part 18 measure.
