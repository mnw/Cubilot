## What exists today

1. A role agent launches with `--plugin-dir <link>/<role>` and `--plugin-dir <link>/shared` (Claude, `pty.rs:902`) or `--skill <link>/<role>/skills` and `--skill <link>/shared/skills` (Pi, `pty.rs:673-675`).
2. `<link>` is the per-agent symlink `<factory dir>/agents/<hex>`. It points to a version folder (`factory.rs:694`, `link_agent`). The launch flags name the link, not the version.
3. A hot reload has two steps in the hub. `POST /factory/relink` (`hub/features/factory.ts:108-140`) moves the link, creates the attempt id and writes `<hex>.pending` (version, reload id, attempt). The bridge calls it only at its idle point (`maybeReload`, `hub/channel/core.ts:276-312`: it returns at once while `busy`). The runtime then reloads: `reload-plugins` for Claude (`claude-mod/register.ts:260-263`), `ctx.reload()` for Pi (`pi-extension.ts:107-125`). `POST /factory/applied` (`factory.ts:143-176`) accepts a report only with the attempt id of `.pending` (409 otherwise). On success it writes `.applied` and `last`; on failure it removes `.pending` and writes `last` = failed. There is no rollback of the link. This path is proven live (factory-roles).
4. A new session deletes the link, `<hex>.applied` and `<hex>.pending` (`clear_agent_records`, `factory.rs:683`; called at `pty.rs:263`). It does not delete other files in `agents/`.
5. The skills of a role are the folders in `<version>/<role>/skills/` and `<version>/shared/skills/` (`stage_role`, `factory.rs:68-96`). The skills come from two places, already merged into the version folder at staging: the bundled `factory/<role>/skills/` and the user layer `<app data>/factory-user/<role>/skills/<name>/` (`apply_user_layer`, `factory.rs:117`, called at `factory.rs:309`; the folder is `app_data_dir().join("factory-user")`, `factory.rs:377`). A user skill with the name of a bundled skill replaces it. A new user skill is in the version hash, so it appears in `current` at the next staging (app start). So the staged folders are the full list, and C6b reads only the staged folders.
6. Claude also has a per-agent settings file with `skillOverrides` (`build_agent_settings`, `factory.rs:496-518`). Today it turns user and project skills off. It does not list role or shared skills.
7. A busy agent keeps its files: the launch flags name the agent link, and only the hub moves it, at the bridge's idle point (`resolve_role_launch` comment, `factory.rs:731-733`).

## 1. List

New Tauri command `agent_skills(agent) -> { role: string | null, mode: "none" | "legacy" | "plain" | "view", relaunch_needed: boolean, groups: [{ name, skills: [{ id, on, state }] }] }`.

1. Role of the agent: the tmux session option `@cubilot_role`, read the way `pty_roles` reads it: `list-sessions -F` with `PILL_FORMAT` and `parse_role_pills` (`pty.rs:478-502`). It is not `CHATBRIDGE_ROLE`: that is only a prefix of the launch command, not the persisted session record. Empty role: `role: null`, `mode: "none"`, no groups. The UI shows the text of C4 ("No role"). An agent that has a role but no skill record is not "no role" (point 2).
2. Mode (separates a legacy agent from a no-role agent). C6b sets a session option `@cubilot_skills` at launch, next to `@cubilot_harness` (best effort, same pattern): `view` (the launch flags name a view), `plain` (a role launch without a view). The option is a record, not proof. The mode is checked against the real launch arguments: C6b reads the pane's start command (`tmux display-message -p -t <agent> '#{pane_start_command}'`), splits it as a shell does, and looks only at the values of the flags `--skill` (Pi) or `--plugin-dir` (Claude B). A value that is `<factory dir>/agents/<hex>.view/...` (the agent's own hex) means `view`. A value that is `<factory dir>/agents/<hex>/...` (the link) means `plain`. Any other result, or a command that cannot be read, means `legacy`. A `.view/` text in another place (an `--append-system-prompt` path, a `CHATBRIDGE_*` value, a user argument, a path of another agent) is not proof and is ignored. When the option and the parsed result differ, the parsed result wins. An agent with a role and no `@cubilot_skills` was launched before C6b: the parsed result decides, and it is `plain` or `legacy`. Legacy and plain behave the same for Pi. For Claude under method A the mode does not matter (the settings file exists for every role launch).
3. `relaunch_needed` is true when the agent cannot receive the choice by Reload: a Pi agent (or a Claude agent under method B) whose mode is `legacy` or `plain` and whose `.skills-off` is not empty. It is false for Claude under method A, and for every agent in mode `view`.
4. Group "Role · <role>": the folder names in `<current version>/<role>/skills/`. Group "Shared": `<current version>/shared/skills/`. Use `current_version_dir()` (`factory.rs:351`).
5. Skill id: `<group>/<folder>`, with group `<role>` or `shared`. Example: `worker/agency-engineering-cms-developer`. The folder name is unique inside a group. It is also the key in the store.
6. `on` = the id is not in `.skills-off` of this agent.
7. `state` is one of `loaded`, `not_loaded`, `new`, derived only from `.skills-applied` (section 2a), never from `.skills-off` and never from a reload that failed:
   - `loaded`: the id is in `applied.skills` and not in `applied.off`.
   - `not_loaded`: the id is in `applied.skills` and in `applied.off`. The agent confirmed that it did not load it.
   - `new`: the id is not in `applied.skills`. The skill was staged after the version the agent last loaded (or the agent has no applied record). It is not loaded, and it is not "confirmed not loaded". It counts as loaded only after a reload whose inventory contains it.
   The list shows the skills of `current`, so a new skill appears at once.

## 2. Store

1. File: `<factory dir>/agents/<hex>.skills-off`. Content: JSON array of skill ids, sorted, no duplicates. Mode 0600. Atomic write by temp file and rename, like `write_agent_settings` (`factory.rs:524-545`). It records the human's intent only.
2. Tauri command `agent_skills_set(agent, off: string[])`. It validates every id against the current list (unknown id: error, nothing written). Empty list: delete the file. Default: no file, every skill on. A write that fails returns the error to the caller and changes nothing; the UI must then show the old choice and the error (it must not show the new box state as saved).
3. Kill and launch again with the same name: the choice stays. `clear_agent_records` deletes only the link, `.applied` and `.pending` (`AGENT_RECORD_SUFFIXES`, `factory.rs:676`). `.skills-off` is not in that list and must not be added.
4. A role change under the same name: ids of the old role no longer match. Unknown ids are ignored when a view is built, and the store is not rewritten.
5. Removing an agent with the x button does not delete the file. A name that is used again gets its old choice (human's decision Q3). The records of section 2a also stay; the next launch of the name overwrites them.

## 2a. Prepared, pending and applied selection (bound to the reload attempt)

Human's rule: an unchecked skill stays unchecked. After the next successful reload that applied it, it shows grey with "not loaded" until the human checks it again. Before that reload, the strip "N change(s) wait for Reload" shows.

The loaded selection must be the one the reload attempt really used. A later click must not change it, and a failed or late report must not change it. So the selection is copied from step to step, and each step is bound to the attempt. The files are in `<factory dir>/agents/`, JSON, mode 0600, atomic write (temp file and rename):

1. `<hex>.skills-prepared` = `{ gen, off: [...], skills: [...], kind }`. Written by the app in `agent_skills_apply` (section 5). `gen` is an integer, one more than the highest `gen` seen in the prepared, pending or applied record. `off` is the snapshot of `.skills-off` used to build. `skills` is the inventory: every skill id of the current version, on or off. `kind` is `view` (Pi, Claude B) or `settings` (Claude A). A newer apply replaces the file and deletes its own older unpublished build. It never touches the published build.
2. `<hex>.skills-published` = `{ gen, off, skills, version }`. The selection that the paths on disk give now: the published view symlink, or the live settings file. Written by the hub in `POST /factory/relink` right after a publication swap (section 5, step 4), and by the launch (point 4). It is not removed by a failed reload, a failed report or a retry: it survives every failure, and it is the single source for the next attempt. It changes only with the swap that it describes: a swap that is rolled back restores the previous record with it (section 5, step 4, failure rules).
3. `<hex>.skills-pending` = `{ attempt, gen, off, skills, version }`. Written by the hub in `POST /factory/relink`, in the same handler that creates the attempt id, for **every accepted reload attempt**: it is a copy of `.skills-published` after the publication step of that handler, whether that step published a newer prepared build or did nothing (a retry after a failed reload, or a Reload with no checkbox change). It carries the attempt id of the `.pending` that the same handler writes. A click or an apply after this point changes only `.skills-off` and `.skills-prepared`; it cannot change `.skills-pending` or `.skills-published`.
4. `<hex>.skills-applied` = `{ version, gen, off, skills }`. Written by the hub in `POST /factory/applied` on success only, and only after the existing attempt check (`b.attempt === order.attempt`, `factory.ts:156-158`). It copies `.skills-pending` after a check that `.skills-pending.attempt` equals the attempt of the report. A report with another attempt gets 409 and changes nothing (a late completion, a duplicate, a report of an old attempt).
5. A launch writes `.skills-published` and `.skills-applied` itself (the launch loads what it builds): the same content, `version` of the agent link, and `gen`, `off` and `skills` of the build it used. A launch without a view or settings override (empty off-list on a Pi agent, section 3) writes `{ version, gen: 0, off: [], skills: [<inventory>] }` to both. It deletes `.skills-prepared` and `.skills-pending`. The reader treats a missing `.skills-applied` as `state: new` for every skill (an agent launched before C6b).
6. Failure rules (no rollback of a reload, as for the link; one rollback exists for a failed publication, section 5):
   - Failed reload (`failed: true`, valid attempt): `.pending` and `.skills-pending` are removed; `.skills-published` and `.skills-applied` are unchanged. The published build stays on disk, so the next attempt (the bridge's retry, `core.ts` `retryWait`, or a click) copies the same `.skills-published` into a new `.skills-pending`, and a success then records it in `.skills-applied` with no new checkbox change. A skill the human re-enabled stays `not_loaded` (checked box, change waits); a skill that was `loaded` stays `loaded`. The row shows Failed. A failed reload never shows "not loaded" for a skill that was loaded.
   - Record write failure in `/factory/applied` (success path): write `.skills-applied` first, then `.applied`, then remove `.pending` and `.skills-pending`. If `.skills-applied` cannot be written: HTTP 500, nothing else is written, `.pending` stays (the same outcome as a failed `.applied` write today: the hub holds the order, the log says restart the agent). The UI keeps the old applied state. If `.skills-applied` is written and a later write fails: the order stays; the next success report of the same attempt rewrites the same content (idempotent).
   - Record write failure in `/factory/relink` (publication): section 5, step 4.
   - Record write failure in `agent_skills_apply` (preparation): error to the caller; the new build is deleted; `.skills-prepared` is not replaced; the published build is not touched.
7. The `.skills-built` file of the earlier draft does not exist any more.
8. States of one skill, from `on` (the box) and `state` (section 1, point 7):
   - `on` and `state = loaded`: checked, normal.
   - `on` and `state = new`: checked, label "new, loads on Reload" (C6c criterion 3). It counts as a change that waits.
   - `on` and `state = not_loaded`: checked, label "not loaded" (normal colour). It counts as a change that waits. This is the state after a failed re-enable: the label stays until a successful reload loads it.
   - not `on` and `state = loaded`: unchecked, normal. It counts as a change that waits. No "off on reload" label.
   - not `on` and `state = not_loaded`: unchecked, grey, text "not loaded". No change waits. It stays so until the human checks the box.
   - not `on` and `state = new`: unchecked, label "new, stays off on Reload". No change waits. After the next successful reload (its inventory contains the id and its off-list contains it) it becomes `not_loaded`. C6c criterion 3 says only "State new: label 'new, loads on Reload'"; for an unchecked skill that text is wrong. C6c must use both labels (Orchestrator to align the ticket).
   - N in the strip = the number of skills where `on` differs from (`state = loaded`).
9. Hub change (part of C6b): the `.skills-published` and `.skills-pending` writes in relink, the lock (section 3, point 3), the copy in applied, the cleanup in the failed branch, tests (section 6).

## 3. Apply for Pi

Pi has no setting that turns one skill off. `--skill` takes a folder. So the folder must hold only the skills that are on.

1. A per-agent view: `<factory dir>/agents/<hex>.view-<gen>/`. It holds `<role>/skills/` and `shared/skills/`. Each entry is a symlink `<skill folder> -> <factory dir>/agents/<hex>/<group>/skills/<folder>`. The target goes through the agent link, so a version change (the hub moves the link) still reaches the right files. The published view is the symlink `<hex>.view -> <hex>.view-<gen>`.
2. Flags: `--skill '<hex>.view/<role>/skills'` and `--skill '<hex>.view/shared/skills'` replace the two `--skill` paths at `pty.rs:673-675`. `--no-skills` stays.
3. Preparation builds `<hex>.view-<gen>/` and writes `.skills-prepared`. It does not touch `<hex>.view`. Publication (the symlink swap) happens in the hub at the reload boundary (section 5). The swap is a temp link and a rename (same pattern as `link_agent`, `factory.rs:694-716`), so a run reads a full old view or a full new view, never a half view. The app deletes the view folders older than the previous published one at the next preparation, so a lazy read through the old path still works for one more generation. The cleanup never deletes a build that `.skills-published`, `.skills-pending` or `.skills-prepared` names, and it runs under the publication lock: the app takes `<hex>.skills-lock` (a folder made with `mkdir`) for the whole of a preparation, and the hub takes the same lock for the whole of the publication step of a relink. The folder holds one file `owner` with one line: `<holder> <pid> <start>`, where `<holder>` is `app` or `hub` and `<start>` is the start time of that process as `ps -o lstart= -p <pid>` prints it. Rules:
   - A holder waits up to 2 s for the lock. After that wait it fails while the owner may be alive: the hub refuses the relink with HTTP 503 (the bridge asks again later), the app returns an error. A lock is never removed because of its age.
   - A lock is removed only when its owner is confirmed dead: the `owner` line parses, the pid does not exist (`kill(pid, 0)` says no such process), or the pid exists and `ps -o lstart= -p <pid>` prints a start time that differs from the owner line (the pid was reused). If the line does not parse, the owner file is missing, or `ps` fails or is unclear, the owner is treated as alive and the lock stays. A lock folder with no owner file younger than 2 s is a taker that is still writing it: wait.
   - A holder releases the lock only when the owner line still names its own `<holder> <pid> <start>`. It never removes a lock whose line names another process.
   - Recovery is serialised (C6b, Validator lock review): a holder that finds a lock with a dead owner takes an exclusive `flock` on `<hex>.skills-lock.guard` (app: `libc::flock`; hub: `flock` through `bun:ffi`; the kernel drops it when the process dies), reads the owner line again under the guard, and removes the folder only if that line is still a confirmed-dead owner. A start time that does not match the `ps -o lstart=` format never proves a dead owner. A removal that fails ends at the deadline, not in a loop. Tested separately in Rust and in the hub; the app and the hub taking the same guard together is not tested.
   So a newer preparation cannot delete a generation that the hub is publishing, and the hub cannot publish a half-written preparation.
4. A Pi agent gets its view only after its first uncheck (human's decision Q1, changed 2026-10-24):
   - A launch with an empty `.skills-off` keeps today's flags byte for byte: `--skill '<link>/<role>/skills'` and `--skill '<link>/shared/skills'`. No view exists. `@cubilot_skills=plain`.
   - A launch with at least one skill off in `.skills-off` builds the view (gen 1), publishes it, and uses the view flags of point 2. `@cubilot_skills=view`.
   - An agent in mode `view` stays in mode `view`. Every later change, also "all on again", prepares a full view and Reload publishes it.
   - The first uncheck on an agent in mode `plain` or `legacy` cannot be applied by Reload: the flags are fixed at launch and name `<link>/...`. `agent_skills` returns `relaunch_needed: true`. `agent_skills_apply` returns that error and builds nothing. After a kill and a launch with the same name, the launch builds the view from the stored choice (section 2, point 3).
   - A launch with no role stays as it is (no view, no change).
5. Pinned launch tests: none of the Pi tests changes, because a launch with an empty off-list is byte for byte as today.
   - `role_validator_pi_flags_have_provider_model_thinking_prompt_skills_and_exclude_tools` (`pty.rs:2625-2645`) and `pi_role_command_has_exactly_two_skill_folders_and_none_inherited` (`pty.rs:2648-2680`) stay as they are. They keep pinning the no-view command.
   - `role_worker_command_loads_the_role_and_shared_plugin_prompt_file_settings_and_model` (`pty.rs:2519-2535`) stays as it is under Claude A and under Claude B (the no-view launch).
   - `build_agent_settings` tests (`factory.rs:1443`, `1490`), Claude A only: they change only if the function gets a new parameter for the off-list. The output with an empty list stays the same. Prefer a separate merge step to keep them untouched.
   - New tests (added, not changed) are in section 6.

## 5. Preparation, publication and reload

C5a is built. `POST /agents/:name/reload` with `force: true` makes the bridge send `/factory/relink` with `force`. The hub orders a reload for the version the agent already has and writes `.pending`. The runtime reloads. The bridge then reports `/factory/applied` with the attempt id.

The click only prepares. Publication happens at the bridge's idle point, inside the relink handler.

Sequence when skills changed (C5b + C6c):
1. The UI calls `agent_skills_set` (the intent, `.skills-off`, is written).
2. The UI calls `agent_skills_apply(agent)`. For an agent that needs a relaunch (section 3, point 4) it returns that error and the UI stops here. Otherwise it prepares: builds `<hex>.view-<gen>` (Pi, Claude B) or the next settings file (Claude A) and writes `.skills-prepared`. It publishes nothing. The running agent's paths are unchanged, also while it is busy. Step 2 may run at every checkbox change. A newer preparation replaces an older unpublished one.
3. The UI calls `POST /agents/<name>/reload` with `force: true`. The bridge calls `/factory/relink` when it is idle; a busy agent waits for the end of the run (`core.ts:276-312`).
4. Publication, in the relink handler (hub), under the lock of section 3, point 3, in this order:
   1. create the attempt id;
   2. if `.skills-prepared` exists and its `gen` is newer than `.skills-published`: save the previous record (`prev = .skills-published`), then swap the published symlink `<hex>.view` to `<hex>.view-<gen>` (Claude A: steps (a) and (b) of section 4 A.2) and write `.skills-published` from `.skills-prepared`. Otherwise nothing is swapped (a retry, or a Reload with no checkbox change);
   3. if `.skills-published` exists, write `.skills-pending` = `{ attempt, ...published }` (a copy of the published selection, so that every accepted attempt has a snapshot); if it does not exist (an agent with no skills record), write none;
   4. write `.pending` with the same attempt id (the existing step).
   Failure rules. A failure in step 3 or 4 undoes this call: remove `.skills-pending`; if step 2 swapped, swap back (the previous symlink target, or `.json.prev` renamed over `<agent>.json`) and then restore `.skills-published` from `prev`. Order of the undo: swap back first, record second. If the swap-back fails, the record is not restored (it still describes the build that is on disk), the answer is HTTP 500, and the next relink sees a `.skills-published` that matches the disk. A failure in step 2 itself (swap or record write) undoes the swap if it happened and answers HTTP 500. In every failure the prepared build is kept: the next relink (the bridge asks again at its next check, existing behaviour) publishes it again. The hub answers 500 with no `.pending`, so the bridge logs "factory relink refused" (existing behaviour).
5. The runtime reloads. A busy agent never reaches step 4, so it keeps its skill paths until its idle point.
6. On success the hub copies `.skills-pending` to `.skills-applied`, but only for the matching attempt (section 2a, point 4). On failure `.skills-applied` and `.skills-published` are unchanged (section 2a, point 6): a retry copies the same published selection and a success records it.

A click during the reload changes `.skills-off` and prepares a newer build. It does not change `.skills-pending`, `.skills-published` or the published build. When the reload of the earlier attempt reports success, the record says what that attempt loaded. The strip then shows the later click as a change that waits (its `on` differs from `state`). The next Reload publishes it.

Window that remains, accepted by the human on 2026-10-24 through the Orchestrator: a run can start during the relink request itself (`core.ts` keeps the order and waits for the run end, `core.ts:303`). Publication has already happened in that case, as the move of the version link does today. The window is one local request. It is not closed, and the busy-agent isolation of step 5 is not unconditional: it holds for a run that is active when the bridge asks. Risk 1. The approval request to the human must say so.

New launch: `resolve_role_launch` (`factory.rs:728`) prepares and publishes the build directly after `link_agent` and before it builds the flags (no run is active), and writes `.skills-applied` (section 2a, point 5). So a new launch uses the stored choice.

## 7. Risks and what is not checked

1. The window of section 5, accepted by the human on 2026-10-24 (through the Orchestrator): a run that starts during the relink request sees the new paths. The busy-run isolation is not unconditional. Also a skill file may be read lazily, and a swap while a run is active can remove a skill the run is about to read. Mitigation: publication only at the idle point, the previous build is kept for one more generation. Not checked on either harness. Closing the window needs a second hub call just before the native reload; not designed.
2. The applied record is the selection the hub published, not a read of what the runtime loaded. If a runtime ignores part of a view (for example a skill it read before the swap), "not loaded" is wrong for that skill. Not checked on either harness; the live checks of C6b (a to d) cover it.
3. An agent without a view needs one relaunch for its first uncheck (human's decision Q1). This is by design, not a gap. It costs the agent's context: a relaunch ends the session. The UI must say so before the human relies on Reload. Agents launched before C6b are in this group (mode `legacy`) and are handled by the same `relaunch_needed` flag.
4. A new version adds or removes a skill. The inventory in the records tells a new skill from a loaded one (section 1, point 7). A removed skill leaves a dead link in an old view until the next preparation. The preparation also runs at every Reload click, so the next reload publishes a current view. A version change with no skills click (the hub moves the link only) does not rebuild the view: a new skill is `new` until the next click. Accepted.
5. Two clicks at once, or two windows: each write is atomic, but the read-modify-write of the off-list is not. Single user, single window. Accepted.
6. The role plugin may need all its skills (a skill that another skill calls). The list does not know dependencies. The human sees only names.
7. Not checked at all: Pi `--skill` accepts a folder that holds symlinks to skill folders (probable, `copy_tree` follows links in staging, but untested for Pi's loader). Claude `reload-plugins` with changed content (the live check of 2026-10-24 covered a changed symlink target only). The `skillOverrides` items of the earlier draft are closed: A failed, see section 4.
8. C6b needs a hub change (section 2a, point 9). The settings-folder environment value of the earlier draft is removed with method A: the hub swaps only the view symlink and the records, all under the factory folder it already knows.
9. The records of section 2a are a new kind of file under the factory folder. CLAUDE.md gets one line in the docs ticket (t_98556c3588740b87), which should also wait for C6c if that is intended (Validator suggestion).
10. Suggestions of the Validator for C6c, not design questions: save and apply errors must be visible and the box must not show a state that was not saved (section 2, point 2); a browser check before the install (focus, full names, status text, count announcements).
