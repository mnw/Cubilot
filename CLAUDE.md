# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Hard rules

- **Never commit unless explicitly asked.** Stage, diff, `git status` — yes. `git commit` / `git push` — no. Exception: a hub-launched stage session (Worker, Writer) commits on its own `ticket/<id>` branch only, never on main, and never pushes. The next stage sees only committed work (human decision 2026-10-24, live check 6.5).
- **Heavy processes run one at a time under `/tmp/cubilot-heavy.lock`.** A full `bun test`, `cargo test`, a `pty-plumbing` run, a stress test or a test hub needs the lock (a lock directory: `mkdir` takes it, `rm -r` releases it, the `owner` file names the holder). `./scripts/test.sh` takes the lock itself and is not reentrant: do not take the lock before you call the script.
- **Never introduce a framework to `ui/index.html`.** The UI is vanilla HTML/CSS/JS by choice. No React, Vue, Svelte, bundler, or build step for the UI. `withGlobalTauri: true` means no bundler is needed to call Tauri commands from JS.
- **The hub port is dynamic, not hardcoded.** The Rust shell binds `127.0.0.1:0` at startup, writes the chosen URL to `~/Library/Application Support/Cubilot/hub.url`, and passes `PORT=<n>` to the `cubilot-bin` sidecar (launched with `CUBILOT_MODE=hub`). Do not reintroduce a hardcoded port anywhere. The webview calls `invoke('get_hub_url')` to learn the URL; the bridge (Claude mod / pi extension) reads the discovery file (or uses `CHATBRIDGE_HUB` env as an override).
- **Agent harness is chosen per agent at spawn and is immutable for the session.** `claude` (default) or `pi` (pi.dev), picked in the spawn modal, threaded `ptySpawn` → `pty_spawn` → `agent_command()` in `pty.rs` (the `Harness` enum). Unknown values are rejected, never defaulted — a UI typo must surface, not silently launch the wrong binary. Changing an agent's harness means killing and respawning, same as room. Both harnesses speak the same hub protocol, so mixed-harness rooms work and nothing hub-side is harness-aware.
- **Pi has no MCP support by design — the chatbridge ships as a pi extension, not a sidecar.** `hub/channel/pi-extension.ts` imports the SAME `core.ts`, `tools.ts` and `hub-client.ts` the Claude mod uses; tool definitions are never duplicated across runtimes. It is bundled by `scripts/build-sidecars.sh` to `src-tauri/resources/pi-extension.js` (gitignored build artifact) and loaded via `pi -e`. **After changing `hub/channel/pi-extension.ts`, `tools.ts`, or `hub-client.ts`, rerun `./scripts/build-sidecars.sh`** — the `.app` loads the bundle, not the TypeScript. Identity reaches it as `CHATBRIDGE_AGENT`/`CHATBRIDGE_ROOM` env on the tmux command, the same way it reaches the Claude mod.
- **Pi agents reuse Claude Code's skills and commands; they do NOT get its MCP servers, plugins, or hooks.** Pi implements the same Agent Skills standard (`<dir>/SKILL.md` + `name`/`description` frontmatter), so `claude_resource_flags()` in `pty.rs` passes `--skill ~/.claude/skills` and `--prompt-template ~/.claude/commands` (plus the project-local `.claude/` equivalents) on every pi spawn without a factory role. A spawn with a factory role (change factory-roles, task 3.3) passes `--no-skills` and only the staged role and `shared` `--skill` folders instead, with no `claude_resource_flags()` folders: pi 1.3.0 also discovers `~/.claude/skills` by itself, so flag order alone cannot pick the factory copy — **project-local paths are passed first** because pi resolves name collisions first-one-wins, which reproduces Claude Code's closest-scope-wins precedence. Only existing paths are passed; pi warns on missing ones. `CLAUDE.md` is read by pi natively. Plugin skills are shared too, but only for plugins listed in `SHARED_CLAUDE_PLUGINS` (currently figma) — resolved through `installed_plugins.json` rather than a pinned path, because the plugin cache keeps stale version dirs beside the live one and globbing the plugin dir double-loads every skill. Keep the list explicit: each skill costs ~155 tokens of system prompt in every request, so sharing a plugin is a judgement call, not a sweep. Claude's MCP servers, marketplace plugins, and `~/.claude/settings.json` hooks have no pi equivalent and are silently absent — don't assume parity when debugging a pi agent that "can't do what the claude one does".
- **Per-agent skill switches keep their state in the factory dir, `<app data>/factory/agents/`, next to the agent link `<hex>`.** `<hex>` is the lowercase hex of the agent name. `.skills-off` is the human's choice, and only the app writes it. `.skills-prepared` is the build the app prepares on a click. A role launch with at least one skill off builds a view, swaps `.view` to it, and writes `.skills-published` and `.skills-applied`. A launch with no skill off builds no view and keeps the link (`launch_in` in `src-tauri/src/skills.rs`). At a reload, `/factory/relink` publishes the prepared build and writes `.skills-pending`. A success report with the matching attempt copies it to `.skills-applied` (`hub/features/factory-skills.ts`, `hub/features/factory.ts`). `.view` links to the built `.view-<gen>` folder, which the launch flags name only after the first uncheck. `.skills-lock` and `.skills-lock.guard` serialise the publication. See `docs/PROTOCOL.md` (`/factory/relink`, `/factory/applied`, `/agents/{name}/reload`).
- **Skills are added per role, not per agent.** There is no per-agent skill add. The limit and its workaround are in `docs/SKILLS.md` ("Known limits").
- **After changing `hub/hub.ts`, rebuild sidecars** (`./scripts/build-sidecars.sh`) before testing. The `.app` runs the compiled binaries, not the TypeScript source.
- **Never mutate `knownAgents`, `agentQueues`, `agentConnections` or `staleTimers` individually.** They are sealed inside `createAgentRegistry()` (`hub/core/agents.ts`); go through the registry (`agents.ensure` / `agents.remove`, aliased `ensureAgent` / `removeAgent` in `hub.ts`) so the four stay in sync atomically.
- **Hub endpoints require auth.** Mutating routes require `Authorization: Bearer <token>`. Read routes (`/agents`, `/presence`, `/stream`, `/agent-stream`, `/image/<id>`, `/handoffs`, `/interrupts`, `/nutshell`) accept EITHER the bearer header OR a `?token=<token>` query param — required because `EventSource` and `<img>` can't set custom headers. The token is minted by the Rust shell, written to `~/Library/Application Support/Cubilot/hub.token` (mode `0600`), and delivered to the `cubilot-bin` hub sidecar via the `CUBILOT_TOKEN` env var. The bridge reads the file; the webview gets it from `get_hub_url`'s return value. `hub.log` is also mode `0600` because tokens land in it via query-string-authenticated requests.
- **Upload allowlist is by file extension, configured in `config.yml` under `attachment_extensions`.** Defaults: `["jpg","jpeg","png","pdf","md","txt"]`. Extension is the single source of truth — no MIME check, no magic-byte check. Magic-byte and MIME checks are bypassable, and execution is prevented regardless of MIME confusion by the serve route's strict CSP (`default-src 'none'; sandbox`) and `X-Content-Type-Options: nosniff`. The Rust shell validates entries (lowercase alnum, ≤10 chars, no dots), passes the cleaned set via `CUBILOT_ALLOWED_EXTENSIONS=jpg,jpeg,…` env. The hub rejects uploads whose filename extension isn't in the set with HTTP 400.
- **Attachments persist to disk at `<CUBILOT_ATTACHMENTS_DIR>/<id>.<ext>`.** No in-memory cache. Rust resolves the dir (config override via `attachments_dir`, legacy `images_dir` still honored; default `~/cubilot-attachments/` — top-level home avoids macOS TCC) and passes it via env. Files are chmod'd 0600 on write. Agents receive absolute file paths in channel text via `[attachment: <path>]`; the hub's `agentEntry()` does the URL→path rewrite. The HTTP route is `/image/<id>.<ext>` (legacy name; serves any allowed extension, not just images).
- **JSON bodies on mutating routes are capped at 256 KiB** (`JSON_BODY_MAX`). `requireJsonBody()` checks `Content-Length` before `req.json()`. Exception: `POST /handoffs` uses 1 MiB (`HANDOFF_BODY_MAX`) to accommodate diffs/contracts in `context`.
- **Every structured-message state change writes exactly one event + one derived-table update in one SQLite transaction.** Applies to `createHandoff`, `acceptHandoff`, `declineHandoff`, `cancelHandoff`, `expireHandoff`, `createInterrupt`, `ackInterrupt`, and the nutshell-update path inside `acceptHandoff` (where the nutshell patch is applied in the SAME transaction as the handoff accept event). Never bypass.
- **Cross-kind transactions.** A ticket-stage launch writes `stage.launching` and `ticket.assigned` (actor `system`) in one transaction. A spec-review launch has no ticket and writes no `ticket.assigned`. The spec-review PASS writes `stage.passed` and one `ticket.queued` for each promoted scope ticket in one transaction. The final PASS of a validator or reviewer stage writes `stage.passed` and, for an `in_review` ticket, one `ticket.done` (low radius) or one `ticket.assigned` to the room lead (high radius; the hub never writes `done` on a high ticket), both actor `system`, in one transaction. These three are the only cross-kind transactions: both kinds commit or roll back together. Do not add a fourth one without updating this line and `docs/PROTOCOL.md`.
- **Broadcasts carry `version = events.seq`.** Clients (UI + agents) reconcile by `(id, max version seen)` across both `handoff.*` and `interrupt.*` kinds. Older versions MUST be discarded.
- **Mutating structured-message endpoints use trust-on-self-assertion.** `by` and `from` are validated against the expected actor for the route but not cryptographically verified. Token-holder can claim any identity. Documented hardening target: per-sidecar tokens bound to agent identity.
- **Terminal-state policy on handoff accept/decline/cancel and interrupt ack.** Same-status-retry → idempotent 200. Different-status-retry → 409 Conflict. Uniform across all transition routes.
- **`/interrupts` kind.** Lifecycle `pending → acknowledged` (terminal). No cancel, no expire. 500-char `text` cap. Not a preemption — cooperative signal only.
- **Briefings re-send on roster/presence change, not once per process.** `hub/core/briefing-dispatcher.ts` owns this: `scheduleFanout()` (500 ms reset-on-call debounce) rebuilds each connected agent's briefing and enqueues it only when its signature (`briefingSignature()` in `hub/core/briefing.ts`: room, peers + online flags, nutshell, summary layer counts) differs from the last one sent to that agent; `forceFanout()` skips the dedup. Permanent members (human) are never briefed. The bridge core delivers a briefing in `context` mode — it never wakes the agent. The last-sent signatures live in memory only; a hub restart re-briefs everyone.
- **Terminal pane uses a raw PTY, not `tmux -C` control mode.** xterm.js consumes tmux's ANSI directly; keystrokes go to the PTY master as raw bytes. Never re-introduce `tmux -C` or `send-keys` for interactive input forwarding — that's what v0.6 broke on. `send-keys` is only allowed for one-shot commands the user invoked explicitly (none in v0.7). The v0.9.8 regression guard at `tests/integration/pty-plumbing.test.ts` asserts raw-PTY mode (no `%output` / `%begin` / `%end` control-mode framing on the attach stream).
- **Any change to `pty.rs`'s `resolve_utf8_locale`, `configure_existing_session`, or `attach_and_stream` helpers SHALL have an integration test scenario covering the affected plumbing before the change ships.** The baseline is `tests/integration/pty-plumbing.test.ts` (7 scenarios across session lifecycle, locale env, remain-on-exit toggle, raw-PTY mode). Per-helper coverage closed the pre-v0.9.5 deferral cycle — without it, pty.rs refactors keep getting pushed to "some future change with tests first". Don't repeat that.
- **tmux sessions need UTF-8 locale env.** Pass `LANG` and `LC_ALL` to both `new-session -e` and `builder.env()` on the attach client. macOS GUI apps inherit a blank / `C` locale from launchd; without UTF-8 in the locale, claude's capability probe downgrades to ASCII output and its logo renders as `____` instead of Braille/box-drawing. Use the user's `LANG` if it already contains `utf`; otherwise default to `en_US.UTF-8` (ships with every macOS install).
- **Terminal sessions use tmux on `~/Library/Application Support/Cubilot/tmux.sock`.** `new-session -d -x 80 -y 24` (dimensions are load-bearing — tmux probes the invoking TTY otherwise, and our Rust shell has no controlling terminal). Wrap every session command in `$SHELL -ic "..."` so `.zshrc` aliases resolve (Anthropic's installer creates `claude` as a `.zshrc` alias, not a PATH binary). The inner command must be passed as a SINGLE tmux argv element so /bin/sh's argv-join doesn't split the quoted `--mcp-config '/path with spaces'` into multiple tokens.
- **tmux sessions survive Cubilot restart.** The Rust shell MUST NOT kill tmux sessions on app exit. Drop the PTY handles (which detaches our `attach-session` client) and let tmux keep running. The pane auto-attaches on next launch via `pty_list()` + `pty_spawn` idempotent re-attach. Also: on every auto-attach, force `remain-on-exit off` on the session — legacy sessions from earlier builds had it ON, which silently holds panes after claude exits and blocks the clean tab-close flow.
- **The chatbridge is a Claude Code mod, not an MCP server. `--mcp-config <path>` carries ONLY the user's own global MCP servers.** Cubilot generates `~/Library/Application Support/Cubilot/mcp-configs/global.json` (mode `0600`) from the user's global MCP config with the `chatbridge` entry filtered out, so a stale user entry can never shadow or duplicate the mod's `mcp__chatbridge__*` tools. Claude loads it additively with the cwd's own `.mcp.json`. Never write to the user's project `.mcp.json`.
- **The mod is staged, never loaded from inside the `.app`.** `lib.rs` materializes it atomically at `~/Library/Application Support/Cubilot/chatbridge-mod/` at startup (sibling temp dir, then rename) and `pty.rs::claude_command` passes that path to `--plugin-dir`. Claude Code writes `.claude-plugin/types/`, `.gitignore` and `tsconfig.json` into every `--plugin-dir` it loads; pointing it into the signed bundle would modify the bundle. Identity reaches the mod as `CHATBRIDGE_AGENT`/`CHATBRIDGE_ROOM` env on the tmux command, same as pi.
- **The bridge core owns policy; adapters implement `Host` only.** Room gate, briefing/nutshell text, the message envelope, delivery mode (`context` / `steer` / `wake`) and the post-delivery check live in `hub/channel/core.ts`. `hub/channel/pi-extension.ts` and `hub/channel/claude-mod/register.ts` supply a `Host` (`hub/channel/host.ts`: request, stream, upload, deliver, log) and wire runtime events to `onRunEnd`/`onToolResult` — nothing else. A policy change made in one adapter is a bug; make it in the core. `tools.ts` and `hub-client.ts` do I/O through the `Host`, never `node:*` or global `fetch`.
- **The mod's tool hook must ask `$.tool.check` before running a chatbridge tool.** It answers the call itself, so Claude Code's permission step beneath it never runs. `deny`, or an `ask` that comes from a user settings rule, refuses the call (a mod tool has no approval dialog — failing closed honours the rule); an `ask` from the permission mode alone runs the tool — so in `default` mode all sixteen chatbridge tools (the nine bridge tools plus `create_ticket`, `claim_ticket`, `transition_ticket`, `assign_ticket`, `attach_ticket_file`, `list_tickets`, `edit_ticket`) run without a prompt. Never remove this check: without it a user's ask/deny rules on `mcp__chatbridge__*` are silently bypassed.
- **`PreToolUse` and `PostToolUse` hooks do not run for chatbridge tools.** Tested live on Claude Code 2.1.306 on 2026-10-21: PreToolUse and PostToolUse hooks from a plugin do not run for mcp__chatbridge__* tools, because the mod answers the call itself. (Evidence: `openspec/changes/factory-roles/tasks.md`, check 0.4; a control hook on `Bash` ran in the same session.) The mod's `tool.call` hook never calls `next(e)`; per the declarations, `next(e)` is what runs "the hooks beneath, then core", and `$.tool.check` "asks no PreToolUse hook or classifier". The user's allow/ask/deny *rules* are still honoured through `$.tool.check`. Hooks in `~/.claude/settings.json` were not tested separately. Do not rely on a hook to police chatbridge tools.
- **`--allowed-tools 'mcp__chatbridge__ack_permission,mcp__chatbridge__post,mcp__chatbridge__post_file'` is still on the claude command (`pty.rs`, pinned by its tests).** It is a leftover of the MCP era, kept on purpose and not yet proven redundant: the three tools already run in `default` mode through the mod, but the allow rule probably still matters in a mode that turns an unresolved `ask` into a deny (the other thirteen tools would then be denied; untested). Removing it, or extending it to all sixteen, needs a live check of `$.tool.check` under such a mode first. Do not delete it as dead code on sight.
- **In the mod, `$` may only be passed to top-level function declarations.** `claude plugin validate` rejects anything else. The `Host` is built in a top-level `makeHost($)` that returns closures over `$`; the core never sees `$`.
- **After changing anything under `hub/channel/**`, rerun `./scripts/build-sidecars.sh` AND `./scripts/check-mod.sh`.** The `.app` loads the bundles (`pi-extension.js`, `chatbridge-mod.js`), not the TypeScript; `check-mod.sh` runs `claude plugin validate` and type-checks `register.ts` against the Claude Code declarations (the root `tsconfig.json` excludes `hub/channel/claude-mod/**`).
- **Claude Code 2.1.296 is the minimum; the app refuses older versions at spawn.** Installed plugins' hooks modules sit behind Claude Code's rollout flag `tengu_plugin_hooks_modules`; on 2.1.287 a stale disk-cached "off" silently disabled the mod in new processes. If a Claude agent never joins (the tab warns after 20 s), check its debug output for "hooks modules not loaded" before suspecting the bridge. Never force the flag (e.g. `DISABLE_GROWTHBOOK`). Claude Code's `stable` auto-update channel lagged at 2.1.287 (2026-10-13) and its auto-updater reinstalled it over 2.1.296; machines running Cubilot need `"autoUpdatesChannel": "latest"` in `~/.claude/settings.json` until stable reaches 2.1.296.
- **Verified against Claude Code 2.1.296 and pi 0.87.1** (first built on 2.1.287). Mods are early access; re-run the spike evidence (`openspec/changes/chatbridge-claude-mod/design.md`, "Spike results") and `test-matrix.md` when either version changes. See `docs/adr/0011-chatbridge-runtime-core.md`.
- **Claude settings (hooks) pass via `--settings <path>`, mirroring the `--mcp-config` pattern.** Cubilot materializes per-agent settings at `~/Library/Application Support/Cubilot/settings/<agent>.json` (mode `0600`, atomic write via tmpfile + rename). Currently registers a single `Stop` hook that writes a sentinel file under `/tmp/cubilot/<CUBILOT_AGENT>/signals/` for the deterministic-tui-capture orchestrator's completion signal. Never write to the user's `~/.claude/settings.json`. The hook command MUST use BSD-userland `date` syntax only (`%s` whole-second epoch); GNU extensions like `%3N` produce literal output on macOS. Sub-second ordering comes from filesystem mtime (`stat -f %m`).
- **`pty_capture_turn(agent, input, timeout_ms)` is the single primitive for deterministic single-turn TUI capture.** Three layers coordinated atomically: geometry (`tmux set-option window-size manual` + `resize-window 240×100`), capture (`tmux pipe-pane -o`), completion (Stop-hook sentinel poll). All cleanup happens regardless of success/failure (pipe-pane disable, window-size restore). Output lands at `/tmp/cubilot/<agent>/captures/turn-<epoch>.log` (success) or `turn-<epoch>.partial.log` (timeout/error — retained for forensics). 10 most recent successful captures retained per agent; older success files pruned, partials never auto-pruned. Caller reads via `pty_read_capture(log_path)` (size-capped, /tmp/cubilot/ path-prefix-guarded).
- **Always use `./scripts/install.sh` for dev rebuilds, never a `pkill + cp` shortcut.** `install.sh` runs an orphan-hub sweep (kills any `cubilot-bin` process with `CUBILOT_MODE=hub` whose ppid is 1, i.e. was reparented to launchd when the previous app died without clean exit). Skip the sweep and accumulated orphan hubs listen on stale ports, agent bridges attach to the orphan instead of the current hub, the agent column shows empty, and you waste an hour diagnosing.

- **Human is a permanent roster member.** Registered at hub startup under the name from `CUBILOT_HUMAN_NAME` (config-overridable, default `"human"`). Excluded from stale cleanup via `permanentAgents`. The chat routing keyword `to: "you"` in the `post` tool is retained for backward compat but is NOT the human's identity in structured messages.
- **Never skip the ad-hoc re-sign step when compiling sidecars.** Bun-compiled binaries inherit a stale Bun signature that macOS Sonoma+ rejects; `build-sidecars.sh` strips it and re-signs. Skip it and the sidecar dies silently at spawn with exit code 137.
- **Never add Windows/Linux/Intel-Mac support speculatively.** macOS ARM64 is the only target.
- **Roster never persists; chat transcript persists only when explicitly opted in per room** via `room_settings.persist_transcript`. Active file `<hash8>-<sanitized>.jsonl` rotates to `<hash8>-<sanitized>.<6-digit-seq>.jsonl` at 10,000 lines — rotated chunks are preserved indefinitely; only `POST /rooms/<room>/clear-transcript` deletes transcript data. SQLite (`ledger.db`) owns kinds; JSONL owns chat — they never overlap. JSONL line format is per-line versioned (`{"v": 1, ...}`); readers tolerate higher versions and partial final lines.
- **Lazy per-Room transcript hydration on first agent reconnect.** When `persist_transcript` is true and an agent reconnects to a Room whose hydration hasn't happened yet in the current Hub process, `RoomHydrator.maybeHydrate(room)` reads up to `chat_history_limit` lines from the active JSONL chunk and replays them through `broadcastUI` (entries flagged `replay: true`). Idempotent per-Room per-process — concurrent same-Room reconnects share one cached promise. **The trigger is connection, not startup**: if the user kills all agents in a Room then restarts the Hub, no agent reconnects → no hydration → Room stays empty (matches v0.10.2's "agents gone = empty room" directive). If only the Hub bounces and tmux sessions survive, agents reconnect → chat repopulates. See `docs/adr/0001-lazy-room-hydration.md`.
- **Phase 3 Room summary lives in `hub/core/room-summariser.ts`; the Summariser interface is in `hub/core/summariser/`; Briefing assembly is `hub/core/briefing.ts`.** The summariser's prompt template lives ONLY in `room-summariser.ts` — adapters (`claude.ts`, future `llama-cpp.ts`, `ollama.ts`) take a fully-assembled prompt as a string and return text. **Never construct prompts inside an adapter** — the dedup-against-Nutshell-and-prior-summaries logic only works if there's one prompt template across all backends. Empty-summary detection is by **bullet count** — lines starting with `- ` only (asterisks rejected because models routinely emit them as markdown sub-list decoration `*   **Item:**` or PHP docblock prefixes ` * @var`, both of which are false positives that let prose / hallucinated code through). The "last summarised line" cache derives from `MAX(end_line) FROM room_summary WHERE room=? AND level=1` — single source of truth, no separate state table. Backfill is fire-and-forget from the Briefing path; the Briefing path itself is read-only. See `docs/adr/0002-pluggable-summariser.md` and `docs/adr/0003-hierarchical-room-summary.md`.
- **Room summary scope is the active JSONL chunk only — rotated chunks are forensic-only.** `RoomSummariser` reads from `activePath(room)`; once a chunk rotates to `<basename>.<seq>.jsonl` it stops being a candidate for new L1 generation. Existing L1 entries that referenced lines in the now-rotated chunk are still valid (line ranges are stable per chunk lifecycle), but content past the last L1 in the active chunk at rotation time is never summarised. v2 candidate: cross-chunk continuous line numbering so summarisation walks the entire transcript history. v1 limitation accepted because (a) most Rooms rotate rarely, (b) the human-curated Nutshell covers strategic history regardless, (c) active-chunk coverage is the high-signal recent-context layer the Briefing actually needs.
- **`<private>...</private>` in chat text is stripped at persistence time, never at delivery.** Live agents and the Webview see private content during the session via the in-memory chatLog + SSE delivery. Only on-disk persistence sinks (the transcript JSONL today; semantic summaries when Phase 3 lands) call `redactPrivate(entry)` from `hub/core/redaction.ts`. Tags are case-sensitive exact-string `<private>` / `</private>`; unclosed tags are left literal; nested tags are stripped greedy to the first close.

- **Permission relay is a hub-first wait in the `classic.PermissionRequest` hook.** The hook `POST /permissions`, then waits on `GET /permissions/:id/wait?timeout_ms=<n>` (default 60 000, hub cap 300 000). `allowed`/`denied` answers the hook, and the local dialog closes without a local answer. On timeout it `POST /permissions/:id/dismiss`es as the agent: 2xx → `next(e)`, so the decision stays with Claude's local dialog; 409 → a verdict won the race, re-read the snapshot (`wait?timeout_ms=0`) and honour it; any other dismiss failure → re-read once, honour a terminal verdict, else `next(e)`. **Every request in the hook is bounded** (`curl --max-time`; the wait passes `timeout_ms + 5000`) — the hook must never hang. Hub unreachable or POST rejected → `next(e)`. On Claude Code 2.1.296 (verified live, M18) the local dialog opens immediately, concurrently with the hook: the room and the terminal race and the first answer wins. A room verdict applies through the hook and closes the dialog; a terminal answer decides at once. After a terminal No the card is dismissed within ~50 ms and a later room click gets 409 (observed on install 9; mechanism not traced). After a terminal Yes the hook keeps waiting until its timeout, then dismisses the room card (it stays visible for up to 60 s; a room click in that window is recorded at the hub but has no effect — known limitation, there is no native signal for a local Yes, and the earlier tool.call-entry heuristic was wrong because the permission prompt runs beneath tool.call's next(e)). On 2.1.287 the dialog waited for the hook (observed in M15/M16). Sender gating via `hub.token` on `/permissions/*` is still the precondition for trusting a verdict; if a future deploy mode drops auth there, the relay hook must be removed in the same change.
- **Permissions have no TTL.** Claude Code's local dialog owns the effective timeout. Never add auto-expiry to the `permissions` table — auto-denying a tool the human actually wanted is annoying, auto-allowing is a security violation, and there is no safe default. Policy-driven per-tool timeouts may land later as a separate feature.

- **All persistent state-machine kinds live in `hub/kinds/<kind>.ts` implementing the `KindModule` contract from `hub/core/types.ts`.** Adding a kind is one file under `hub/kinds/` + one entry in the `KINDS` array in `hub/hub.ts`. The orchestrator (routes dispatch, reconnect replay, briefing tool aggregation) is kind-agnostic — never add kind-specific branches to `hub.ts`. Route handlers receive a `HubCapabilities` object (DB + scoped agents + scope-typed SSE emit + auth + events + config); they never reach for module-level globals.
- **Broadcasts use `cap.sse.emit(entry, scope)`.** Never enumerate agent queues from inside a kind. Scope enum: `{ kind: "broadcast" }` · `{ kind: "to-agents", agents: string[] }` · `{ kind: "ui-only" }` · `{ kind: "room", room: string }`. The `emitWhere(entry, predicate)` escape hatch exists but kinds should prefer named scopes.
- **Tickets require acceptance criteria, and an agent moves a `high` blast-radius ticket to `done` only after the human's Allow (the human may complete it directly).** `hub/kinds/ticket.ts`. The approval is an ordinary `permission` request (`tool_name: "ticket:done"`) created by `POST /tickets/:id/approval` together with the ticket's `approval_request_id` pointer in ONE transaction (one `permission.new` event; the pointer is a derived link, not a ticket event). The gate accepts only the pointed-to request with `status = 'allowed'` AND `resolved_by` = the human name — an agent's Allow never opens it. Rework (`in_review → in_progress`) clears the pointer. Ticket events reach agents in `context` mode and are not replayed on reconnect, except that `ticket.new`/`ticket.assigned` wake the assignee once (not the creator of its own new ticket), an unassigned ticket wakes the room lead (`GET/POST /rooms/:room/lead`) to triage it, and the human's answer on a `ticket:done` approval wakes the requester. The human may move an open ticket to any column (agents keep the fixed lifecycle); `done` and `cancelled` stay terminal; the agent's own open tickets come through the `briefingLines` hook, and every ticket change calls `cap.briefing.refresh()`.
- **A `draft` ticket starts nothing, and an open blocker stops a claim.** `hub/kinds/ticket.ts`. A `draft` ticket cannot be claimed (409) and `ticket.new` / `ticket.assigned` wake no one while it is `draft`. `draft → queued` is done by the human or the room lead and writes the ledger event `ticket.queued`; the hub broadcasts `ticket.promoted`, on which the bridge wakes the assignee (or the lead for an unassigned ticket, unless the lead made the move). The lead gets 403 when a non-terminal ticket of the same `request_id` in the same Room has `blast_radius: high`; the human is never refused. A ticket with no `request_id` is checked alone. `claimTicketVerb` answers 409 `blocked by <id> (<status>)` while any `blocked_by` ticket is not `done`; a `cancelled` blocker still blocks (remove it from the list), and the human is not gated. `blocked_by` rows (`ticket_blockers`) change in the same transaction as the ticket's event; the cycle check and the claim gate read them in `decide()`, which holds only while the hub is the single writer of `ledger.db` and `dispatch()` has no `await` between read and write. `request_id` and `blocked_by` change by the human, the ticket's creator or the room lead (not the assignee), only while the ticket is `draft` or `queued`, except by the human. Like the `high` gate, the human-only parts are advisory against a token holder (see Accepted risks).
- **The hub decides launches. The Rust shell only executes them.** The hub never starts or stops an agent session. (It runs `git` subprocesses for the worktrees.) It queues `launch` and `close` requests on `GET /launches/stream`. `src-tauri/src/launches.rs` reads the stream, calls `pty_spawn` or `close_session`, and answers each request on `POST /launches/<id>/ack`. The shell decides nothing and never runs git. The hub creates the worktree before it queues the launch. One function queues launches: `enqueueLaunch` in `hub/kinds/stage.ts`. Only the stage evaluator and the retry path call it. Only `hub/kinds/stage.ts` may import `hub/core/launch-queue.ts`. `tests/unit/launch-queue.test.ts` checks both. No route and no chatbridge tool has a launch parameter. A close kills only the named session. The shell never kills sessions on app exit. Any `hub.token` holder can read the launch stream and send acks, because there is no per-role token. The code path is the only control (see Accepted risks).
- **Stage state changes go through the stage API only.** `hub/kinds/stage.ts` (`createStageApi`) writes each move as one `stage.<status>` event and one `stage` row update, with actor `system`. The statuses are `queued`, `launching`, `running`, `retrying`, `passed` and `failed`. A stage has at most two attempts. No endpoint directly accepts a stage-create or arbitrary-transition command. A `to_role` handoff can create a stage through the evaluator. Some routes cause fixed moves from their input. The launch ack moves `launching` to `running`, or ends the attempt on an error. The turn-end report can stop a `running` stage (to `retrying` or `failed`). A valid result handoff moves `running` to `passed`. Stage events go to the UI only (`ui-only-ambient`). `stage.reminder` and `stage.rejected` go to the stage's own session. The launch queue, the end-of-turn counts and the time-out clocks are in memory. At hub start, each stage that is still `launching` counts as a launch with no ack.
- **`system` is the hub's own actor, never a caller's.** It is in `RESERVED_NAMES`. `hub/core/dispatcher.ts` examines the JSON body of every mutating request. It returns 400 when `by`, `from`, `actor`, `voter`, `requester`, `agent` or `creator` is `system`. Hub code writes `system` for stage moves, the launch assignment, the spec-review PASS, the final-failure handoff to the room lead, and handoff expiry. The bridge delivers a `ticket.assigned` from `system` in `context` mode. Thus its own assignment does not wake the launched session.
- **Validator and Reviewer stage worktrees are read-only.** `hub/core/worktrees.ts` creates them detached. It runs `chmod -N` and `chmod a-w` on the work tree, but not on the root `.git` entry or on symlinks. Then it checks every entry with `access(W_OK)`. If one entry is still writable, it refuses the launch. The roles also block `Edit`, `Write` and `NotebookEdit` (`disallowedTools` in `factory/<role>/<role>.md`). It is not checked whether a pi session (the Validator's harness) applies `disallowedTools`. Worker and Writer stages use the worktree of the `ticket/<id>` branch. The other roles get a temporary detached worktree. The hub removes it when the stage ends.
- **`CUBILOT_STAGE_ID` marks a hub-launched session.** The hub puts the stage id in the launch request. `pty.rs` passes it as `-e CUBILOT_STAGE_ID=<id>` on `tmux new-session`, only for a stage launch. The bridge reads it through `Host.stageId()`. It reports each end of turn to `POST /stages/<id>/turn-end`. A session without the variable is an ordinary agent and reports nothing. Do not set it by hand on a normal spawn.
- **Nutshell is not a kind — it's a document.** Single-row (per room); no lifecycle; no broadcast fan-out to both parties. Lives standalone in `hub/nutshell.ts`. Its write path piggybacks on the handoff primitive (task prefix `[nutshell]`, `context.patch` carries the new text) — that coupling is why `hub/kinds/handoff.ts` imports from `hub/nutshell.ts`.

- **Rooms are immutable per agent.** Captured on the first `/agent-stream` connect via `&room=<label>` (from the `CHATBRIDGE_ROOM` env the bridge was launched with). Subsequent reconnects ignore the arg. To change an agent's room, kill the agent and respawn. The human has `room = null` — super-user, implicitly in every room. Never add a route that mutates an existing agent's room mid-session.
- **Cross-room mutations are 403 for non-human senders.** `POST /handoffs`, `POST /interrupts` (single + bulk), and `POST /permissions/:id/verdict` all reject cross-room sends unless the sender/voter is the human. Bulk interrupt (`{ rooms: [...] }`) is human-only by rule — agents bulk-targeting other rooms would be a denial-of-attention vector. Never relax these without also deciding what abuse looks like.
- **`target: "all"` from the human requires a `room` body field.** The hub returns 400 `"room required for broadcast to 'all'"` otherwise. "All" is ambiguous across projects, and silently interpreting it as "every room" is worse than forcing the caller to be explicit. The webview composer passes the currently-selected room automatically.
- **Nutshell is per-room, not single-row.** The `nutshell` table has `room TEXT PRIMARY KEY`. Edits flow through the handoff primitive as before, with an added `context.room` field that the accept path respects. The human can patch any room; non-human senders can only patch their own. `GET /nutshell?room=<label>` is required — no-arg returns 400. Agents receive the same-room nutshell on connect via briefing AND live via `nutshell.updated` fan-out to same-room queues.
- **The bridge core enforces the room as defense-in-depth.** Even though the hub routes by room, `hub/channel/core.ts` compares `room` on every inbound event against its configured `CHATBRIDGE_ROOM` and drops concrete mismatches with a `host.log` line (null/absent room = system/global, let through). Never remove this gate on the theory that the hub is correct — a regression in routing should surface as drop-log noise, not silent context pollution in an agent's session.

- **Chat slash commands bypass the hub.** A `/`-prefixed message in the composer routes through `pty_write` (Tauri IPC) to the per-agent tmux PTY — NOT through `POST /post`. Bytes go direct to the agent's terminal. The chat log gets one synthetic `system` audit entry per send (in-memory; lost on hub restart). Slash sends require a concrete room (not `All rooms`) and explicit `@agent`/`@all` targeting. The two constants `BUILTIN_SLASH_COMMANDS` and `DESTRUCTIVE_SLASH_COMMANDS` live in `ui/features/slash-discovery.js` — review on each Claude Code release because built-ins drift between versions and the destructive list gates the multi-agent confirm modal.

## Accepted risks (known, not bugs)

- **A token holder can act as the human, so `blast_radius: high` is advisory.** Any agent that can run Bash can read `hub.token` (mode `0600`, same user) and send `by: "<human name>"`. That opens the ticket approval gate (`/permissions/:id/verdict`, or `/tickets/:id/transition` as the human), and lets it dismiss any permission request (`/permissions/:id/dismiss`). The gate holds against an agent that reports its own name honestly (an agent's Allow never opens it), not against a hostile one. Accepted until per-agent tokens bound to identity exist; do not describe the high-radius gate as enforcement.
- **The launch stream has no per-role token.** Any holder of `hub.token` can read `GET /launches/stream` (the prompts and the stage ids of every launch) and send `POST /launches/<id>/ack`. A forged ack can mark a launch `running` that never started, or end an attempt. Launches are gated by code path only (`enqueueLaunch`). Accepted for the same reason as the item above. Fix it together with per-agent tokens.
- **`devtools` feature is on in release builds** (`src-tauri/Cargo.toml`). Ships the WKWebView "Inspect Element" / Cmd+Opt+I console in the installed app so end-user bug reports can include console logs. Consequence: any local process that can attach to the webview can read the token out of `window` / console. Accepted because the hub is loopback-only and the trust boundary is "anything on this Mac as this user is already inside." Revisit if the hub ever moves off `127.0.0.1`.
- **`post_file` follows symlinks.** `Host.upload` stats with symlinks followed (`statSync` in `hub/channel/node-host.ts`, `$.fs.stat` and `curl -F` in the Claude mod), not `lstatSync`. An agent passing `/tmp/link-to-id_rsa` would exfiltrate the target. Not privilege escalation (agents run as the user) but a compromised tool-use path could abuse it. Accepted because rejecting symlinks is security theater unless we also sandbox the entire path — agents already have full fs access. Treat `post_file` as "agent opens this file and sends its bytes."
- **Persisted transcripts may capture secrets.** A user opting `persist_transcript = true` for a room accepts that anything pasted into chat (tokens, API keys, debug dumps) ends up on disk in plain UTF-8 under `transcripts/<basename>.jsonl`. Mode 0600 file + 0700 dir is the only protection in this version — no encryption, no auto-redaction. Default off keeps the boundary at the user's explicit opt-in.
- **Rotated transcript chunks accumulate without auto-delete.** A busy opted-in room over months reaches hundreds of MB across many 5 MB chunks. Footprint is surfaced in the room-persistence UI; `POST /rooms/<room>/clear-transcript` removes everything atomically. Users wanting capped history can `mv` chunks out of the data dir periodically.

Full test run: `./scripts/test.sh [bun test args]` is the default. It takes the heavy lock itself. It runs `bun test "$@"`, so arguments pass through. It applies a time limit and a memory limit. ## Architecture

Two processes bundled into one `.app`, plus an in-process bridge inside each agent runtime:

1. **Tauri Rust shell** (`src-tauri/src/lib.rs`) — spawns `cubilot-bin` (with `CUBILOT_MODE=hub`) as a sidecar on startup, kills it on exit, streams its stdout/stderr to `~/Library/Logs/Cubilot/hub.log`, and stages the Claude mod folder. Exposes one `#[tauri::command]` for external sessions: `get_mcp_template()` (legacy name) returns a `claude --plugin-dir …` launch line.

2. **cubilot-bin** (`hub/main.ts` dispatches on `CUBILOT_MODE`; `hub/hub.ts` is the hub, Bun-compiled by `build-sidecars.sh`) — HTTP + SSE server on `127.0.0.1:<port>` where `<port>` is OS-assigned at app startup (via the Rust shell) and passed in via the `PORT` env var. Owns all state: chat log, per-agent message queues, presence counts. `hub.ts` is the composition root: generic routes live in `hub/features/*.ts` (`HubFeature`), state-machine kinds in `hub/kinds/*.ts` (`KindModule`), shared plumbing in `hub/core/`. **Roster is fully dynamic** — `ensureAgent(name)` is called the first time a name appears on `/agent-stream`, auto-registering it with a hash-derived HSL color. `/post` never registers an agent: an unknown sender gets 409 "connect /agent-stream first" (a post that created the agent would pin it to the default room, because the room is fixed by its first stream). No `agents.json`.

3. **Bridge** (`hub/channel/core.ts` + one adapter per runtime — no separate process) — one instance per agent session, living inside the agent: the Claude Code mod (`hub/channel/claude-mod/register.ts`, bundled to `chatbridge-mod.js`) or the pi extension (`hub/channel/pi-extension.ts`, bundled to `pi-extension.js`). Resolves the hub via `CHATBRIDGE_HUB` env (if set) or the paired discovery files (`hub.url` + `hub.token`); re-reads both on each retry so stale values self-heal. Tails `/agent-stream?agent=<name>&room=<label>` and delivers each event into the agent's context in `context`, `steer` or `wake` mode. Registers the `post`, `post_file` and kind tools (`mcp__chatbridge__*` in Claude). Sends `Authorization: Bearer <token>` to the hub; on 401 (token rotated), re-reads the token file once and retries.

Data flow:

```
agent session ─► bridge (mod / pi extension) ─► hub /post ─► chat_log ─► all ui_subscribers (SSE /stream)
                                                    └─► all agent_queues  (SSE /agent-stream)
webview  ───────► hub /send ────────────────────────► chat_log ─► ui_subscribers + agent_queues
```

### Key invariants

- **Drop-oldest queue semantics.** Bounded `DropQueue<T>` in `hub/core/sse.ts` — when full, oldest item is evicted, not pushed. Prevents a slow subscriber from indefinitely growing memory.
- **SSE heartbeats every 15s + `idleTimeout: 0`** on `Bun.serve`. Without both, Bun kills long-idle SSE connections after 10s by default, which silently breaks agent message delivery during quiet periods.
- **Message dedup by server-assigned `id` + session id.** Each chat entry gets a monotonic `id`. Client persists `lastSeenId` and `serverSession` in `localStorage`. On reconnect, client sends both as query params so the hub skips already-seen entries. Hub restart mints a new session id → client resets dedup state.
- **Reserved agent names:** `you`, `all`, `system`. Validator also enforces `[A-Za-z0-9_.-]` with spaces allowed in the middle, max 64 chars.
- **Stale-agent removal.** When an agent's last SSE connection drops, a 15s timer is armed (`STALE_AGENT_MS`). If no reconnect arrives, the agent is auto-removed from the roster. Reconnecting cancels the timer. Manual removal via `POST /remove` or the × button on an offline agent's row in the agent column is also supported.

### Bundled resource path resolution (Rust)

`resolve_pi_extension()` and `resolve_chatbridge_mod_js()` in `lib.rs` try the same candidates:
- `Contents/Resources/resources/<file>` and `Contents/Resources/<file>` (bundled app — `bundle.resources` keeps the source structure)
- `../../resources/<file>` relative to the executable (during `tauri dev`)

Keep all of them working when changing how bundled resources are located. The Claude mod is then staged out of the bundle (see the hard rule on staging).

## Research-preview caveats

- The Claude Code mods API (function hooks: `register(on)`, `$`, `classic.PermissionRequest`, `$.prompt.submit`, `$.session.append`) is early access and may change between Claude Code releases. Verified on 2.1.296 (first built on 2.1.287). If the bridge goes silent after a Claude Code update, run `./scripts/check-mod.sh` first, then the spike checks in `design.md`. There is no MCP fallback.
